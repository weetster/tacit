# 0077 - Phase 5 maintenance/debug metrics

**Status:** Accepted
**Date:** 2026-05-09
**Phase:** 5, Stage 3
**Closes:** [phase-5-plan.md Stage 3](../plans/phase-5-plan.md)

## Context

Phase 5 is a short evidence gate, not a density phase and not a broad tooling
phase ([ADR 0076](0076-phase-5-short-gate.md)). The Stage 2 baseline already
produced a blind authoring-surface run record under
`plans/phase-5-results/019e0f6b-7b6f-7832-98a0-a5c72e7545be/`. Before that run
is interpreted as evidence for or against Phase 6, the project needs a metric
definition that separates maintenance-specific costs and outcomes rather than
collapsing them into one token or pass-rate number.

The Phase 3 metrics ADR ([ADR 0055](0055-p3-metrics-schema.md)) is the closest
precedent, but it is optimized for fresh-generation corpus grading. Phase 5
needs different slices:

- starting-state failure class
- one-shot versus final recovery
- program recovery versus explanation correctness
- recurring language-primer cost versus workflow prompt cost
- tool/schema feedback cost versus generated output
- human review burden

The benchmark is small and open by design. That means the metric should favor
clear per-task accounting over a large aggregate schema, and it must remain
scorable from the existing Stage 2 artifacts without re-running the model.

## Decision

**Phase 5 is scored as a multi-bucket maintenance/debug record on the
authoring-facing `main.taca` surface. No single aggregate number is the gate.**

The Stage 2 baseline is interpreted using one run record plus a Phase 5 metric
summary with five groups:

1. Surface and artifact integrity.
2. Outcome and recovery rates.
3. Context and token costs.
4. Failure-shape breakdown.
5. Human review cost.

Canonical-`main.tac` control runs, if performed later, are descriptive only.
They must be reported separately and cannot satisfy the primary Phase 5 gates in
place of the authoring-surface run.

### 1. Required source artifact

The authoritative input for Phase 5 scoring is the `phase5-eval` `run.json`
plus its per-task subdirectories:

- `run.json`
- `task-id/starting/*`
- `task-id/turn-N/prompt.txt`
- `task-id/turn-N/raw-response.txt`
- `task-id/turn-N/result.json`
- optional `generated.taca`, `explanation.txt`, and `inspection.txt`

If these artifacts are incomplete, the run is descriptive only and cannot
support the Stage 4 decision ADR.

### 2. Outcome and recovery metrics

Phase 5 reports the following task-level outcome buckets on the authoring
surface:

- `one_shot_pass_rate`
  Definition: fraction of all benchmark tasks that pass on turn 0.
- `final_pass_rate`
  Definition: fraction of all benchmark tasks that pass within the allowed
  repair budget.
- `program_final_pass_rate`
  Definition: fraction of repair + edit tasks whose final generated program
  typechecks, compiles, and meets the exit/stdout condition.
- `explanation_final_pass_rate`
  Definition: fraction of explanation tasks whose final explanation contains
  the benchmark-required concepts.
- `repair_recovery_rate`
  Definition: among tasks that fail on turn 0, fraction that pass by the final
  turn.
- `avg_model_calls_per_task`
  Definition: total recorded turns divided by task count.

Phase 5 also reports recovery by starting-state failure class:

- `compile_type_recovery_rate`
  Denominator: program repair tasks whose starting artifact fails `tacit check`
  or `tacit compile`.
- `behavior_recovery_rate`
  Denominator: program repair or edit tasks whose starting artifact compiles but
  exits with the wrong code or stdout.
- `explanation_correctness_rate_one_shot`
  Denominator: explanation tasks only, scored on turn 0.
- `explanation_correctness_rate_final`
  Denominator: explanation tasks only, scored on the final turn.

These outcome metrics are the primary evidence. They answer the Phase 5
question directly: can the current Phase 4-era surface repair and explain small
maintenance tasks on the prompt-facing authoring representation.

### 3. Context and token-cost metrics

Phase 5 separates four token buckets. They must never be collapsed into one
"Tacit cost" number without preserving the components.

- `language_primer_tokens_total`
  Definition: `model.primer_tokens * total_model_calls`.
  This is the recurring cost of the Tacit-Lite language primer.
- `workflow_primer_tokens_total`
  Definition: tokens from any separate workflow/runbook prompt artifact supplied
  uniformly per model call.
  For the recorded Stage 2 baseline this value is `0`, because no separate
  workflow prompt artifact was injected beyond the harness prompt template.
- `tool_context_tokens_total`
  Definition: tokens of repair-only machine feedback injected after a failed
  turn, including serialized structured diagnostics, inspection text, and any
  explicit tool-result prose generated by the harness.
  If later harness revisions record these pieces separately, the separated
  fields are authoritative; otherwise they are reconstructed from the stored
  repair prompt inputs.
- `generated_output_tokens_total`
  Definition: sum of `turn.generation_tokens` across all turns, including both
  Tacit program output and explanation prose.

Two descriptive derived ratios may be reported:

- `primer_share = language_primer_tokens_total / total_tokens`
- `repair_feedback_share = tool_context_tokens_total / total_tokens`

where `total_tokens` is the sum of the four token buckets above.

### 4. Failure-shape breakdown

Every non-passing turn is classified by `failure_stage` using the existing
artifact values:

- `api`
- `extract`
- `typecheck`
- `compile`
- `run`
- `explanation`

Phase 5 reports:

- count of failures by `failure_stage`
- count of recovered failures by `failure_stage`
- per-task turn history for any task that needed repair

This is descriptive, not gating. The purpose is to distinguish "the current
surface is missing a tool" from "the current surface is adequate but one task
needed another repair round" or "the explanation missed a concrete noun."

### 5. Human review cost rubric

Phase 5 records a review burden per task:

- `low`
  One-shot pass, or one repair with a single localized failure and a final
  result that matches the task condition cleanly.
- `medium`
  Multiple repair turns, or an explanation miss that requires reading both the
  benchmark prompt and the diagnostic/inspection evidence to confirm that the
  final answer is specific enough.
- `high`
  Unrecovered failure, extraction/API failure, or a repaired result that still
  requires manual judgment beyond the benchmark pass condition.

The run-level `human_review_cost` is reported as:

- counts of `low`, `medium`, `high`
- `high_review_fraction`

This cost is descriptive but decision-relevant. A run that barely passes by
mechanical metrics while concentrating review burden in `high` tasks is not
equivalent to a run whose failures are self-localizing and quickly repaired.

### 6. Phase 5 gates

Phase 5 uses three gates and several descriptive metrics.

The gates are:

1. `artifact_integrity_gate`
   Passes iff the run contains the full prompt/response/diagnostic/result record
   needed for later review.
2. `program_recovery_gate`
   Passes iff `program_final_pass_rate = 1.0` on the authoring surface.
   Rationale: the benchmark includes only six small open program tasks. Any
   unrecovered program failure is a concrete blocker for claiming the current
   tool surface is adequate.
3. `explanation_gate`
   Passes iff `explanation_final_pass_rate = 1.0` on the authoring surface.
   Rationale: the explanation slice is only two tasks and both were selected to
   test specific diagnostic/inspection affordances. Missing either one means a
   benchmarked explanation mode is not yet reliable.

The following are descriptive, not gates:

- `one_shot_pass_rate`
- `repair_recovery_rate`
- `avg_model_calls_per_task`
- all token-cost buckets
- failure-stage breakdown
- human review cost

These descriptive metrics still matter for the Stage 4 decision ADR. They
distinguish "good enough to proceed" from "passes narrowly but points to one
obvious pre-Phase-6 tool" without turning every descriptive number into a hard
threshold.

### 7. Reporting format

Phase 5 reports one summary block per run with at least:

- run id, model id, provider, primer hash, primer tokens
- task count by class
- one-shot and final pass counts
- program and explanation final pass counts
- recovery rates by starting-state class
- total model calls and average calls per task
- the four token buckets
- failure-stage counts
- human-review counts
- gate verdicts

The existing `run.json` remains the raw source artifact. A later machine-readable
Phase 5 metrics file may be added, but it must preserve these buckets and must
not merge them into a single density or productivity scalar.

## Alternatives considered

### Reuse the Phase 3 metrics file unchanged

Rejected. Phase 3 metrics are shaped around fresh generation, Python/Rust token
comparison, and corpus test execution. They do not separate explanation
correctness, tool-feedback context, or human review burden in the way Phase 5
needs.

### Gate on one scalar such as token total or final pass rate only

Rejected. A maintenance/debug gate needs to distinguish recovery quality from
cost shape. A run with perfect final pass rate but pathological repair burden
is different from a run with the same final pass rate and clean one-shot
behavior. Likewise, a token total that hides primer cost and repair feedback
cost is not decision-useful.

### Make every metric a hard threshold

Rejected. The benchmark is intentionally small. Hard-thresholding every
descriptive metric would create false precision and invite overfitting to an
8-task gate. The gates should stay minimal while the rest of the record remains
available for judgment in Stage 4.

## Consequences

- The recorded Stage 2 baseline can now be interpreted without changing the
  metric after the fact.
- Phase 5 decisions must discuss authoring-surface program recovery and
  explanation correctness separately.
- Primer cost, workflow cost, tool-feedback cost, and generated output remain
  auditable as separate buckets.
- A future narrow pre-Phase-6 tool can be justified by a specific failure-shape
  or review-cost pattern rather than by vague dissatisfaction with the baseline.
- No sealed-corpus contents, paths, or metadata are required for this metric.
