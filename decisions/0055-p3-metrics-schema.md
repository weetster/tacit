# 0055 — Phase 3 metrics JSON schema

**Status:** Accepted
**Date:** 2026-04-28
**Phase:** 3, Stage 1
**Closes:** [phase-3-plan.md Q-P3-9](../plans/phase-3-plan.md)

## Context

Phase 3 produces three streams of measurements that all need to be
written to disk in a uniform, machine-readable format:

1. **Primary track** — open-corpus and sealed-corpus runs of the
   evaluation (Stages 7–9): for each task, did the model produce a
   program that compiles, typechecks, and passes the task's tests, and
   how many tokens did it cost.
2. **Maintenance sub-track** — repair / edit / refactor tasks
   ([ADR 0053](0053-p3-maintenance-subtrack.md)): pass/fail plus
   maintenance-specific metrics like diff locality.
3. **Cross-family sub-track** — the same primary and maintenance
   measurements run against `openai/gpt-5.5` and a DeepSeek/Qwen open
   weight via OpenRouter ([ADR 0054](0054-p3-cross-family.md)).

A single schema covering all three avoids three parallel reporting
codepaths and makes downstream analysis (the "30% reduction" gate, the
"Sonnet > 70% pass rate" gate, regression comparison across models)
mechanical. Phase 2's [ADR 0041](0041-p2-structured-error-format.md)
already pinned a JSON envelope for type and effect diagnostics; Phase 3
metrics reuse it verbatim for compile/typecheck failures rather than
inventing a parallel format.

The output of `corpus-eval` is paired with the `run.json` metadata file
defined in [ADR 0052 § Run metadata](0052-p3-eval-model-contract.md).
`run.json` records what was run (model id, primer hash, sampling
parameters, timestamps); the metrics file records what came out (per-task
results, aggregates, gate verdicts). Splitting the two keeps the metrics
file replayable: a metrics file can be regenerated from per-task model
outputs and the harness, without re-invoking the model.

## Decision

**Phase 3 metrics are emitted as a single JSON object per
`corpus-eval` run, written to
`plans/phase-3-results/<run-id>.metrics.json` and paired with the
`<run-id>.run.json` produced by ADR 0052. The schema version is `p3.0`.
Compile and typecheck failures embed an [ADR 0041](0041-p2-structured-error-format.md)
diagnostic envelope verbatim.**

### Top-level object

```json
{
  "schema_version": "p3.0",
  "run_id": "<string — matches the paired run.json>",
  "track": "primary" | "maintenance" | "cross-family",
  "scope": "open" | "sealed" | "maintenance",
  "model": {
    "provider": "anthropic" | "openrouter",
    "id": "<model id, e.g. 'claude-sonnet-4-6'>",
    "primer_hash": "<BLAKE3 of primer bytes>",
    "primer_tokens": N
  },
  "tasks": [ … task result objects … ],
  "aggregates": { … aggregate object … },
  "gates": { … gate verdict object … }
}
```

`run_id` is a UUIDv7 generated by the harness and shared with `run.json`.
`track` and `scope` are independent: the primary track has scope `open`
or `sealed`; the maintenance track always has scope `maintenance`; the
cross-family track inherits its underlying scope.

`primer_hash` and `primer_tokens` are pinned at run-start to detect
primer drift across runs being compared. `primer_tokens` is the
authoring-view token count under `o200k_base` per
[ADR 0051](0051-p3-tacit-token-rule.md).

### Task result object — primary track

```json
{
  "task_id": "arithmetic/001-sum-to-n",
  "stdlib_dominated": false,
  "compile_pass":   true,
  "typecheck_pass": true,
  "tests_pass":     12,
  "tests_total":    12,
  "generation_tokens":     42,
  "python_baseline_tokens": 58,
  "diagnostics": null,
  "duration_ms":   2840,
  "retries":       0
}
```

- `task_id` is the path under `corpus/tasks/` (forward slashes,
  no leading slash, no `reference.tac` suffix). The same task identifier
  is used by `corpus-tokens` and `corpus-verify-sealed`.
- `stdlib_dominated` mirrors `corpus/stdlib-dominance.toml` per
  [ADR 0021](0021-corpus-stdlib-dominance-reporting.md). Pinned per task
  so consumers can recompute aggregates without re-reading the dominance
  file.
- `compile_pass` is `true` iff `tacit compile` exited 0.
- `typecheck_pass` is `true` iff `tacit check` exited 0. If
  `compile_pass` is `true`, `typecheck_pass` is also `true`
  (compile implies check passed).
- `tests_pass` / `tests_total` count harness test cases that passed; if
  the program failed to compile, both are `0`.
- `generation_tokens` is the model output (the fenced Tacit-Lite block,
  stripped per [ADR 0052 § Output extraction](0052-p3-eval-model-contract.md)),
  measured per ADR 0051. **Primer tokens are not duplicated here**; the
  primer is fixed across all tasks in a run and lives in `model.primer_tokens`
  at the top level. Aggregates apply primer cost per ADR 0051.
- `python_baseline_tokens` is the Python `reference.py` count under the
  same tokenizer per [ADR 0019](0019-corpus-idiom-rules.md). It is
  written into each task entry rather than recomputed at aggregate time
  so the metrics file is self-contained.
- `diagnostics` is `null` on full success; otherwise it is the verbatim
  ADR 0041 diagnostic envelope (`{"schema_version": "p2.0", "errors":
  [ … ]}`) emitted by `tacit check` or `tacit compile`. For test
  failures (compile passed but a test case returned the wrong value),
  `diagnostics` is an ADR 0041 envelope with a single error of kind
  `test-failure` (Phase 3 introduces this kind for the metrics file
  only; it is not a typechecker diagnostic).
- `duration_ms` is wall-clock end-to-end including model call, compile,
  typecheck, and test execution.
- `retries` counts transient-error retries per
  [ADR 0052 § Retries](0052-p3-eval-model-contract.md). `0` on a clean
  run.

### Task result object — maintenance track

```json
{
  "task_id": "maintenance/repair/003-broken-quicksort",
  "subtype": "repair" | "edit" | "refactor",
  "compile_pass":   true,
  "typecheck_pass": true,
  "tests_pass":     8,
  "tests_total":    8,
  "diff_locality":  0.18,
  "starting_tokens":   95,
  "generation_tokens": 110,
  "diagnostics": null,
  "duration_ms":   3120,
  "retries":       0
}
```

- `subtype` records which sub-track per ADR 0053.
- `diff_locality` is the fraction of the starting program's bytes
  replaced by the edit. Reported for all subtypes; the ≤30% locality
  threshold from ADR 0053 is gating only for `repair` and used for
  reporting on `edit` / `refactor`. `null` if the model produced
  whitespace-only output or the program failed to parse such that no
  diff can be computed.
- `starting_tokens` is the authoring-view token count of the input
  program (`broken.tac` for repair, `starting.tac` for edit / refactor).
- `generation_tokens` is the full output token count, not the diff. Diff
  size is captured by `diff_locality`.
- `stdlib_dominated` and `python_baseline_tokens` are absent — there is
  no per-task Python baseline for the maintenance track.

### Task result object — cross-family track

Same schema as primary or maintenance, with `model.provider` set to
`openrouter`. No new fields. Comparing a Sonnet primary run to a
GPT-5.5 cross-family run is a join on `task_id` between the two metrics
files.

### Aggregate object — primary track

```json
{
  "full": {
    "task_count":       47,
    "compile_pass_rate":   0.83,
    "typecheck_pass_rate": 0.81,
    "tests_pass_rate":     0.74,
    "tacit_tokens_total":   78640,
    "python_tokens_total":  81230,
    "token_delta":        -0.032,
    "primer_amortized_total": 78640
  },
  "stdlib_dominated": { … same shape … },
  "non_stdlib_dominated": { … same shape … }
}
```

- The three keys (`full`, `stdlib_dominated`, `non_stdlib_dominated`)
  match ADR 0021's three-way split.
- `task_count` is the number of tasks in the bucket.
- The `*_pass_rate` fields are fractions in `[0, 1]`. `tests_pass_rate`
  is task-level: a task contributes `1` if all its tests passed, else
  `0`. (Per-test pass counts are aggregated separately; see
  `tests_pass_total` / `tests_total_total` below.)
- `tacit_tokens_total` is the **primer-inclusive** sum per
  ADR 0051: `sum_over_tasks(primer_tokens + generation_tokens)`. The
  primer is therefore counted N times for an N-task aggregate, matching
  how the model is actually invoked.
- `python_tokens_total` is the sum of `python_baseline_tokens` across
  the bucket.
- `token_delta` is `1 - tacit_tokens_total / python_tokens_total`.
  A negative value means Tacit-Lite is denser; the Phase 3 gate requires
  `token_delta ≤ -0.30` on `full` and `non_stdlib_dominated`.
- `primer_amortized_total` reports `primer_tokens + sum(generation_tokens)`
  (primer counted **once**) for diagnostic comparison only; it is **not**
  the gate-relevant figure.

Two additional totals support per-test-case reporting:

```json
{
  "full": {
    …,
    "tests_pass_total":  342,
    "tests_total_total": 401
  }
}
```

These let downstream analysis distinguish "passed all tests in 35 of 47
tasks" from "passed 342 of 401 individual test cases."

### Aggregate object — maintenance track

```json
{
  "by_subtype": {
    "repair":   { "task_count": 6, "compile_pass_rate": 0.83, "tests_pass_rate": 0.67, "diff_locality_mean": 0.21 },
    "edit":     { … },
    "refactor": { … }
  },
  "overall": { "task_count": 12, "compile_pass_rate": 0.75, "tests_pass_rate": 0.58 }
}
```

No token-delta field — there is no Python baseline for maintenance
tasks. `diff_locality_mean` is the mean over tasks where
`diff_locality` is non-null; null entries are skipped, not zero-valued.

### Gate verdict object

```json
{
  "primary_pass_rate_gate": {
    "applies":  true,
    "metric":   "tests_pass_rate",
    "scope":    "full",
    "threshold": 0.70,
    "value":     0.74,
    "passed":    true
  },
  "primary_token_gate_full": {
    "applies":  true,
    "metric":   "token_delta",
    "scope":    "full",
    "threshold": -0.30,
    "value":     -0.032,
    "passed":    false
  },
  "primary_token_gate_non_stdlib": {
    "applies":  true,
    "metric":   "token_delta",
    "scope":    "non_stdlib_dominated",
    "threshold": -0.30,
    "value":     -0.41,
    "passed":    true
  }
}
```

The harness writes whichever gates apply to the run. Maintenance and
cross-family runs set `applies: false` for the primary gates and emit
their own (currently: maintenance runs gate nothing — they are
reporting-only per ADR 0053; cross-family runs emit reporting-only
deltas vs the paired Sonnet run, with no automatic pass/fail).

A single `passed_overall: bool` at the top of the gates object is
`true` iff every gate with `applies: true` has `passed: true`. Absent
on runs with no applicable gates.

### File location and naming

```
plans/phase-3-results/
  <run-id>.run.json        — ADR 0052 metadata
  <run-id>.metrics.json    — this schema
  <run-id>.outputs/        — per-task raw model outputs (optional retention)
    arithmetic/001-sum-to-n.txt
    …
```

`run-id` is shared between the metadata and metrics files. The
`outputs/` directory is opt-in (off by default to keep result bundles
small); when present, each file contains the verbatim model output
before fenced-block extraction, useful for debugging unparseable
responses.

`plans/phase-3-results/` is checked in for representative runs only —
the directory is not a complete history. Per [ADR 0053](0053-p3-maintenance-subtrack.md)
and the cross-family ADR, weekly representative runs are committed; ad
hoc runs are kept locally.

### Schema versioning

`schema_version: "p3.0"` is the initial Phase 3 schema. Bumps:

- **Patch** (`p3.0` → `p3.0` with field additions only): allowed
  without a new ADR if the addition is purely additive (new optional
  field, defaulting to `null`).
- **Minor** (`p3.0` → `p3.1`): backward-incompatible field removals or
  type changes require a new ADR.
- **Major** (`p3.0` → `p4.0`): a Phase 4 successor schema is a
  separate ADR.

The harness validates incoming metrics files against the version it was
built for; mismatched versions exit non-zero rather than silently
misinterpreting fields.

### Backward compatibility with `corpus-tokens`

The existing `corpus-tokens` command continues to emit a flat CSV of
per-task token counts and is not replaced by this schema.
`corpus-tokens` is for ad hoc inspection of source-file token counts
(no model invocation); the metrics schema is for `corpus-eval`'s
end-to-end run output (with model invocation).

A consumer can derive the `python_tokens_total` aggregate from a
metrics file and a `corpus-tokens` CSV — the per-task numbers must
agree by construction.

## Alternatives considered

- **One file per task; aggregates computed at read time.** Simpler
  writer, but every consumer must reimplement aggregation, and the
  three-way ADR 0021 split must be reapplied each time. Rejected: write
  the aggregates once, in the harness, where the data is freshest.

- **Embed `run.json` metadata inside the metrics file.** Unifies into a
  single file. Rejected: the metrics file should be regeneratable from
  per-task outputs without re-invoking the model; mixing in
  model-call metadata (request IDs, latency, etc.) couples the two
  concerns. Pairing by `run-id` is cheap and keeps the regeneration
  path clean.

- **Reuse Phase 2's `schema_version: "p2.0"` rather than introducing
  `p3.0`.** Rejected: the top-level shape differs (p2.0 is a flat
  `{schema_version, errors[]}` envelope; this schema has tasks,
  aggregates, gates). Embedding p2.0 envelopes inside `diagnostics`
  preserves diagnostic compatibility without conflating the two
  schemas.

- **Separate metrics schemas for primary, maintenance, and
  cross-family.** Three writers, three readers. Rejected: the
  per-task shape only differs by a few fields; keeping a single
  envelope with optional fields is simpler than three near-duplicate
  schemas. The `track` and `scope` fields disambiguate.

- **Include the primer text in the metrics file.** Useful for full
  reproducibility, but the primer is large (~10K tokens, ~40KB) and
  the same primer is reused across many runs. Rejected: store the
  primer hash; the primer text lives at `plans/primer/tacit-lite-primer.md`
  and is content-addressed by hash like any Tacit artifact.

- **Use Protocol Buffers / FlatBuffers instead of JSON.** Would catch
  schema violations at compile time. Rejected: JSON matches Phase 2's
  diagnostic envelope, is human-readable for incident review, and the
  schema is small enough that JSON Schema validation suffices. A
  formal `docs/phase-3-metrics.schema.json` is delivered in Stage 7.

- **Compute the token-reduction gate as primer-amortized.** Sums
  primer once per run, not per task. Rejected by ADR 0051 and
  reaffirmed here: the gate-relevant figure is primer-inclusive
  per-task, since each model invocation pays the full primer.
  `primer_amortized_total` is reported only as a diagnostic.

- **Inline test-case-level results (per-test pass/fail).** Already
  available in `tests_pass` / `tests_total`. Per-test detail is rarely
  needed at aggregate time and would balloon the file. Rejected for
  the schema; per-test detail is recoverable by re-running an
  individual task with `--verbose`.

## Consequences

- **The harness's `corpus-eval` command writes a `<run-id>.metrics.json`
  alongside its `<run-id>.run.json`.** Both files share `run_id` and
  live under `plans/phase-3-results/`.
- **Phase 2's diagnostic envelope is reused verbatim** for compile and
  typecheck failures, including the new `test-failure` kind introduced
  here for Phase 3 metrics. Consumers that already parse Phase 2
  diagnostics need no changes to read Phase 3 failure details.
- **Aggregates are pre-computed.** A reader gets the three ADR 0021
  buckets and the gate verdicts without recomputation. Recomputing from
  the per-task array remains possible (and recommended for any reader
  that does its own analysis).
- **Schema versioning is explicit.** Phase 4 changes require a version
  bump and a new ADR; in-place silent changes are not permitted.
- **The metrics file is self-contained for the gates it reports.**
  `python_baseline_tokens` per task and `primer_tokens` at the top
  level mean a reader does not need access to `corpus/` or the primer
  file to verify the gate verdicts.
- **A formal JSON Schema lives at `docs/phase-3-metrics.schema.json`
  and is delivered in Stage 7.** It validates all outputs of
  `corpus-eval`. CI runs the validator on any committed
  `<run-id>.metrics.json` under `plans/phase-3-results/`.
